# 工作汇报写作规范

## 默认结构

```markdown
**本周进展：**

1. <工作主题>。<为什么重要>。<难点>。<采取的方法和验证结果>。

2. <工作主题>。<为什么重要>。<难点>。<采取的方法和验证结果>。

**后续计划：**

1. <与本周进展直接衔接的下一步>
```

根据时间范围将标题替换为“今日进展”“近三日进展”“阶段进展”或“月度进展”。

## 表达风格

- 使用无主语、动作优先的项目汇报语气。禁止出现第一人称代词；直接写“完成、修复、验证、定位、推进”等动作和结果。
- 优先使用业务人员能直接理解的语言；每一项都要写清“具体出了什么问题、影响了谁或哪个流程、采取了什么处理、现在结果如何”，不能只写抽象术语。
- 禁止使用抽象管理词或抽象工程术语代替具体问题；无法避免的技术名词必须在同一句中解释清楚。
- 每个事项按“为什么做 → 为什么重要 → 为什么耗时/难 → 怎么做 → 结果如何”组织，避免把版本号、提交号、测试数量等过程记录直接当成成果。
- 每个大项通常写一至三段；同一功能下的独立修复不要省略，使用“已修复/已处理/已补齐”清单保留覆盖度，但不要把每个中间尝试都写成一条。
- 技术名词和关键数字保留，但必须先说明具体现象、影响和处理结果；页面级细节只在能说明问题是否解决时出现。
- 用“完成、修复、验证、定位、推进”等可核验动词；没有完成证据时使用“开始排查、正在推进、计划”。
- 测试结果写清通过、跳过和未验证范围，不用“全部正常”代替证据。
- 环境排障默认不作为主要成果，除非它解决了部署、协作访问或交付阻塞。

## 已完成事项与修复清单

主段落之后使用清单补充独立工作项。`已完成：` 用于承载重要、能体现工作量和交付价值的事项，例如跨模块改造、真机验证、生产部署、关键问题定位、数据漏算修复或流程贯通。

`已完成：` 清单要精选，不追求把全部修复都列进去，通常每个主题保留 3 至 7 项；次要修复、界面细节、状态展示和小范围兼容问题并入前面的段落。每条都必须是一句完整的话，写清动作、对象或问题、结果或验证，并加粗核心技术对象或已验证结果。

```markdown
已完成：

- 完成 **2D 建图一键联合流程重构**，将连接、启动、停止保存和上传合并为并发流程，减少现场重复操作。
- 完成 **服务器定位建图从容器接口确认到真机出图的完整验证**，3D 和 2D 作业均产出可固化地图包。
- 完成 **标注工作量漏算修复**，将未质检但已提交的标注框计入工作量并部署到生产环境。

已修复：

- 修复 SSH 输出撑宽页面的问题，通过限制网格和子元素最小宽度避免移动端横向溢出。
- 修复压缩 MCAP 魔数常量错误，避免有效压缩包被误判为无效文件。
```

`已完成：` 清单优先选择体现工作量和交付影响的事项；次要问题放入 `已修复：` 或 `已补齐：`，同样保持一句话说明。相关小问题可以合并，但不要把中间尝试、单条命令或单纯测试数量写成一项。

## 内容边界

- 用户提出需求不等于已经完成。必须结合后续完成记录判断。
- 多个会话重复讨论同一功能时，使用最新确认结果，同时保留其中独立完成的分析、修复、部署和验证项；重复的续写或镜像记录只计一次。
- 报告开始前先逐个会话建立覆盖清单。每个非闲聊、非纯请求会话都必须落入报告主题，或记录明确的不纳入原因。
- 不根据常见问题补写本次并未观察到的现象。
- 不把统计方法不同的数量直接相加，也不把累计次数当作去重后的数量。
- 后续计划只能从未完成事项或已完成工作的自然延伸中提炼。

## 数据源说明

汇报末尾用一行说明实际使用的数据源，区分“已读取”和“未能访问”内容。例如：

```markdown
数据源：本地 Codex 会话、SSH 项目与服务器会话记录、语义地图/标注项目飞书群聊与文档；已合并重复会话，未读取无关群聊和未授权私有内容。
```

这些来源是本用户的默认数据源，不需要每次重新指定；只有用户明确缩小范围时才排除其中一类。数据源说明只能写实际读取到的内容，不能把计划读取、搜索结果摘要或用户提出但未完成的事项当作工作证据。

## 默认篇幅

- 1 天：2 至 4 个主要事项，约 500 至 900 字。
- 3 至 5 天：3 至 5 个主要事项，约 900 至 1600 字。
- 1 个月：按项目主题归并，约 1500 至 2500 字；独立问题很多时允许增加清单长度，不能用篇幅上限裁掉已处理事项。

用户要求精简版时，每项压缩为一至两句话；要求详细版时，可以增加证据和结果，但仍按主题归并。
