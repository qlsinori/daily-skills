# clean up

用于 Mac 等主机通过 Deskflow 控制 Ubuntu 接收端时，检测并释放 X11 记录的残留按键。调用本 skill 即授权一次检测和释放，不必再次请求确认。

若用户描述的是打字时输入法显示卡顿，先参考下方“输入法显示卡顿的用户经验”，不要直接当作残留按键处理。

1. 确认执行环境是出问题的 Ubuntu 接收端的图形会话。不要默认 SSH 所在机器就是目标，不要猜测 DISPLAY 或使用 sudo。目标不明确时先澄清。
2. 提示用户“请暂时松开所有键，我会检测并清除残留按键状态”。
3. 在 skill 目录运行 `python3 scripts/release_keys.py --release`。脚本输出按下键的 keycode、名称、释放列表和复查结果。仅查询时使用 `python3 scripts/release_keys.py`。
4. 释放后再运行一次仅查询，区分即时释放成功与状态再次出现；邀请用户试打字，以用户确认作为实际恢复的依据。没有检测到按下键时，不宣称已修复。释放后仍有按键或用户反馈复发时，进入下方流程，不循环释放。

脚本仅支持 Linux 原生 X11；Wayland 的 XWayland 查询不能代表整个桌面的输入状态，遇到 Wayland 或无法打开显示时停止此修复路径并说明原因。不得自动重启 Deskflow、终止进程、改映射、修改截图快捷键或安装依赖。

这里清除的是当前按下状态，不是 Caps Lock/Num Lock 等锁定状态，也不处理鼠标按钮。按键残留只证明接收端状态异常，不能单凭此结果断言 Deskflow 漏掉了松开事件。历史案例中曾同时检测到左右 Shift、Escape 和未命名 keycode；每次应重新查询，不硬编码这些键。

## 释放后复发

- 先仅查询当前按键并检查 Deskflow 连接。`Control_R` 是接收端的逻辑键名，不能据此要求苹果键盘用户寻找不存在的右 Ctrl；也不要把按左 Ctrl 当作可靠的替代修复。
- 日志查询限定 Deskflow 进程或服务，避免输出无关的整段用户日志。若 stdout/stderr 是交给 GUI 的管道，说明日志需从 Deskflow 界面查看，不读取管道或声称已排除连接故障。
- 一次释放后仍复发，可指导用户在控制端 Deskflow 手动 Stop → Start，操作时松开所有修饰键。不要自动重启或终止进程。
- 用户确认重连完成后重新查询。重连不保证清除 Ubuntu 已记录的按键；若仍残留，提示用户松开所有键，再执行一次 `--release`，随后独立仅查询并请用户试打字。这是连接状态改变后的单次恢复，不是循环释放。若再次失败，停止释放，继续诊断控制端日志、映射和输入事件来源。

## 已验证案例与解释边界

2026-10-20：首次释放右 Ctrl 后即时查询为空，但随后右 Ctrl 再次出现；苹果键盘按放左 Control 无效。用户在 Mac 端 Stop → Start 后，Ubuntu 查询仍有左右 Ctrl。随后单次释放两键，即时及独立复查均为空，用户确认恢复。

据此可确认最终释放清除了接收端的残留按下状态，且组合操作后恢复。重连可能重置了 Deskflow 的连接或内部输入状态，但本例没有事件级日志证明这一机制，也不能证明重连是必要条件、哪一端漏发了松开事件，或左右 Ctrl 来自哪个实体键。说明原因时明确区分这些事实与推测，不将本例写成所有键盘异常的通用根因。

## 输入法显示卡顿的用户经验

用户于 2026-10-20 补充此前的排查结果：通过 Deskflow 打字时，输入法显示曾出现卡顿；Mac 端切成中文后正常，切成英文则卡顿。这里的日期是记录日期，问题实际发生时间未提供。

以后遇到同类显示卡顿，优先提醒用户检查 **Mac 控制端** 的输入法或输入源，切成中文后再次试打字。不要误写成切换 Ubuntu 接收端输入法，也不要仅因显示卡顿就执行按键释放或重启 Deskflow。若同时有 Ctrl/Shift 卡住等迹象，再按上方流程检测残留键。这是用户在当前使用环境中验证的处理经验，具体机制未确定，不推广为所有 Deskflow 环境的通用结论。
