## Safety Gates

- Before commit, review `git status --short`, `git diff --stat`, and `git diff --check` in the release repository.
- The release repository must be on a clean, synchronized `develop` base. Never create or push `release/*` or `codex/mapdb-*` branches for a release.
- Preserve unrelated changes in the release repository. When publishing only the requested change, use an isolated clean checkout of synchronized `develop` and set `MAPDB_RELEASE_REPO`; port only reviewed changes. Do not stash, reset, or publish someone else's work. The release script stages all changes in its target checkout, so review that entire checkout before execution.
- Never retag or force-push an existing version.
- The CI deploy waits for active mapping work and rolls back a failed health check. Do not bypass that guard.
- Retained library source records may keep `uploading` status after ingestion. The idle gate excludes only positive, complete byte counts with strict `library_ready`, `library_upload`, and `upload_fingerprint_verified` boolean markers. Real uploads and queued/claimed/mapping work remain blocking; malformed metadata or missing columns remain conservative. Never cancel retained data records merely to pass deployment.
- Configure production secrets only in the host `mapdb.env` or protected CI variables. Use stdin or a permission-restricted file when transferring a secret.
- Destructive model cleanup requires a read-only reference audit first and must retain every weight required by current mapping, detection, navigation, or historical-map compatibility.

## Dependency and Build Preflight

Distinguish the **code release tag** from the **dependency image tag**: code-only releases mount an immutable release directory onto an older verified image. A healthy new release need not have a newly built image.

Before tagging, inspect the running image ID and its OCI revision, then compare dependency inputs against that revision (not merely the last code release). Use `semantic_mapping/docker/mapdb/validate_code_release.py` to identify blocked paths. Keep provenance, ancestry, idle-job and rollback checks enabled.

- Python/UI/API/docs changes normally reuse the dependency image without Docker build or package installation.
- A change to `pip-base.lock.txt` may reuse only when the deployment verifier proves it merely adds exact pins already installed, with their transitive requirements satisfied, in a fresh offline container from the immutable candidate image ID. Never infer this from a mutable running container or remove a required dependency declaration to force reuse.
- The reviewed editor evaluator addition has one narrow image-extension path: `extend_editor_dependency.py` accepts only the newly added `python-quickjs-ng==0.12.1.1` Linux x86_64 abi3 wheel with its source-reviewed SHA-256. After the same immutable image, OCI ancestry and dependency-input gates, download exactly that wheel with `--require-hashes --no-deps`; build an offline child layer on the verified parent image and verify the resulting dependencies in a fresh offline container. It must not upgrade installed packages, accept another missing distribution, compile native code, or download Torch/CUDA. Record the parent image ID, wheel hash and new image ID. A failed extension must leave the running service unchanged; never reinterpret it as authorization for a full build.
- Removed/changed pins, missing packages other than that exact reviewed evaluator addition, other dependency inputs, native code and Dockerfile changes require analysis before a dependency build. The deploy script stops by default before `docker build` if reuse cannot be proven. Determine which inputs changed, which stable layers should be cached, and whether the environment already satisfies the change. Only when a dependency build is necessary, supply `MAPDB_ALLOW_DEPENDENCY_BUILD=1` and a concise `MAPDB_DEPENDENCY_BUILD_REASON` for that specific pipeline. Existing user authorization may cover this decision; do not add a redundant confirmation step. Never persist the override as a default project variable. Full builds import a retained release image's BuildKit cache and export inline cache metadata. Keep dependency COPY/RUN layers ahead of runtime code; never introduce routine `--no-cache` or age-only aggressive pruning.
- The reviewed September 10 runtime repair has a separate narrow extension in `extend_runtime_dependency.py`: accept only the verified immutable v2.68.0 parent, its OCI ancestry and exact reviewed Dockerfile change adding `openssh-client`, plus hash-pinned entrypoint/healthcheck scripts. Refuse source `mapdb.env`; preserve the existing private host configuration. Build only while the fixed runner host lock is held. If SSH is already installed, build offline; otherwise permit only the reviewed SSH OS package set without upgrades/removals. Never run pip/Conda or rebuild Torch/CUDA. Verify parent filesystem layers, all installed Python versions, Torch/CUDA versions and runtime script hashes in fresh offline containers before activation. Do not accept container-commit images with mismatched tag/OCI provenance. Any other dependency delta still requires normal build analysis.
- Older images without inline metadata cannot restore cache already lost. Do not promise zero downloads for a real dependency build; inspect plain BuildKit output to distinguish cache misses from dependency changes.

If build logs unexpectedly begin large Torch/CUDA downloads, intervene before activation: compare immutable inputs and cache evidence, stop an unnecessary build, verify the old service remains healthy, then fix the decision or cache handling. Do not let an unexpected full download run unattended merely because CI is green.

Run deployment validators locally before publication: shell syntax, `validate_code_release.py --self-test`, `verify_installed_dependencies.py --self-test`, `dependency_image_candidates.py --self-test`, `validate_docker_cache_layout.py`, and `validate_runtime_recovery.py`. After publication confirm that the pipeline used the predicted reuse/build path. A canceled build is not a deployment; verify the old service remains healthy, fix the cause and publish a fresh tag.

## Concurrent Releases and Waiting-for-Resource Recovery

Before publication, reconcile the latest remote develop SHA and tags with nonterminal deployment jobs and the active production tag. Multiple coding tasks may work independently, but designate one publisher for the same production host: review and sequence their releases instead of having each agent create tags and retry deployments independently. Recheck remote state immediately before pushing; never overwrite concurrent work or reuse a tag another publisher allocated. The host lock serializes deployment execution, not commit/tag allocation or release ordering. Before retrying an older job, compare its tag/SHA with production and newer queued releases; use a fresh reviewed rollback tag rather than accidentally downgrading the service.

Do not interpret the UI label alone as proof of concurrent deployment:

| Observed state | Evidence to inspect | Response |
| --- | --- | --- |
| `created` | Required validators and latest job attempts | Diagnose stage scheduling; do not start deploy ahead of successful validators. |
| `pending` | Matching protected runner, actual running jobs and service/request logs | Repair runner matching or polling; restart only the idle dedicated runner when justified. |
| `waiting_for_resource` | Resource-group upcoming jobs, any holder information supported by this GitLab version, and target deployment processes | Distinguish a real deployment from stalled GitLab resource assignment. An empty queue or unsupported holder endpoint alone does not prove a database lock is free. |
| Host wrapper exits 75 | Actual holder of the fixed host lock and its deployment process | Wait for the legitimate holder, then retry the still-intended release. Never unlink the lock file: that can create a second inode and allow parallel deployment. |
| All latest required jobs succeeded, pipeline still `running` | Individual job results, deployed tag/SHA and production health | Report delayed aggregate status separately; do not restart or redeploy a healthy release merely to change the UI badge. |

For stuck legacy resource-group jobs, record job/pipeline IDs, tag/SHA, statuses and ownership first. Cancel only superseded releases within the authorized scope; do not cancel unrelated active work. Verify cancellation at the job level, the old queue, and absence of surviving target deploy/build/compose processes before changing serialization or retrying. A canceled pipeline badge is not proof that remote processes stopped. Do not keep creating new resource groups or release tags to work around the same queue: a new group also stalled in this incident. Preserve the current complete host-lock wrapper and retire all historical jobs that bypass it; inspect delayed older pipelines before handoff. Project-level cancellation does not constitute a GitLab database-lock reset. If an actual server-side reset is needed, use an already authorized administrative entry; do not invent a reset endpoint or claim a reset without evidence.

Incident evidence (2026-09-08): no other running project job was found, superseded deployment queues were emptied, and both the old and newly created GitLab resource groups still failed to dispatch. Therefore concurrent publication was a risk to manage, not a proven explanation for this stall. The fixed production-host lock allowed the v2.66.111 deployment job to finish in approximately 56 seconds; immutable dependency-image reuse avoided Docker build and package downloads. During that deployment a real lock contender exited 75; after completion it could acquire the lock. GitLab aggregate pipeline status still lagged successful individual jobs. Do not generalize this as proof that every waiting job is a stale lock or that all GitLab scheduling faults have been repaired.

## Runner and Skill Maintenance

The production tag pipeline uses the dedicated `mapdb-dual5090` project runner on the dual-GPU host. It is protected, accepts no untagged jobs, and runs one job at a time. All deployment validators use the host's Python 3; this workflow does not pull a validation image. All future tags run the complete deployment through `run_deploy_locked.sh` on that host, holding `$HOME/.local/share/mapdb-runner/deploy.lock` with `flock` from before source staging through health/rollback and cleanup. GitLab resource-group assignment is not used: even a newly created group stalled in the observed incident. The lock file may remain after exit; the kernel lock is released automatically, so never delete the file to unlock it. A contender exits 75 before deployment. This guarantee requires the sole protected shell runner to remain on the production host under the same account; do not move it or bypass the wrapper. The user service `mapdb-gitlab-runner.service` must be enabled, active and survive logout through loginctl linger.

Before publication and whenever jobs remain pending, inspect the matching runner's tags, protection, pause state, **manager `contacted_at`**, running jobs and actual service state. GitLab's `online` flag and API `contacted_at` are coarse/cached indicators, not real-time liveness probes. An older timestamp plus no running jobs does not prove a runner fault or another deployment. Check service/container state, sanitized request/job logs and a real job before concluding that polling stopped. Distinguish missing pipeline creation, created-stage scheduling, pending-runner matching and actual execution. A `prepare environment` failure on the shell executor happens before SSH deployment: check noninteractive profile loading first. The installer only guards the standard logout `clear_console` block for interactive terminals, preserves a backup and checks login-shell startup. Never replace a custom profile or print it indiscriminately.

Use ordinary retries of the same immutable tag after fixing a concrete failure. If an idle runner's job polling needs refreshing, restart only its dedicated service after confirming no active job; do not restart MapDB or require new SSH credentials. Never retry deployment ahead of successful required validators or remove the host transaction lock, idle or rollback gates. The legacy host is not a fallback. After migration, do not retry historical deployment jobs that use either retired GitLab resource group; publish a fresh rollback/fix tag through the current pipeline. Before changing serialization, cancel superseded deploy jobs, verify terminal states and an empty old queue, and confirm no target deploy/build process remains. Never use a per-release lock or remove serialization. Repair the dedicated service or configuration and confirm it takes a real tag job. Never print runner config.toml or auth tokens while diagnosing it.

If an SSH-pushed tag resolves to the reviewed SHA through repository APIs but has no pipeline and Pipeline Create returns `Reference not found`, distinguish this from a resource lock. Recheck before intervening. A project owner may create one new higher protected annotated tag through the GitLab tag API at that exact reviewed SHA, recording the recovery rationale in the tag annotation, then request and verify its pipeline. Never delete, move or force-push the old tag. This exceptional same-commit recovery tag uses its annotation as the version rationale; the existing commit changelog remains unchanged. Verify protection, peeled SHA, required validators and deployment serialization. Cancel superseded deployments and watch for delayed pipelines before declaring completion. API-created recovery tags worked in the observed incident; repository-cache or post-receive causes remain unconfirmed without server evidence. Do not turn this exception into routine tag churn or claim pipeline creation proves deployment.

The versioned skill lives beside deployment scripts at `semantic_mapping/docker/mapdb/release_skill/`. Keep local skill changes and this snapshot synchronized in every release. `scripts/release_mapdb.sh` invokes `scripts/sync_release_skill.py` automatically; `--check` verifies equality. Credential paths and environment-variable names are references, not credential values. Review the snapshot diff before publishing; the scanner does not replace that review.
